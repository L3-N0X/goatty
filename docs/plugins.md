# Plugins (Stage 5)

A goatty plugin packages a command-line tool so that someone who has never used it gets a good setup in one click: goatty downloads the tool into its own directory, shows its most useful options on the **Plugins** settings page with plain-words explanations, and wires those settings into goatty's managed zsh. Nothing outside goatty's directories changes, and nothing runs as root.

Code: `crates/goatty-plugin` (format, trust, bin `goatty-plugin`), `crates/goatty-shell/src/plugins/` (on a host: registries, plans, installs, rendering), `crates/goatty-app/src/settings_window/plugins.rs` (the page). Repositories: [goatty-registry](https://github.com/goatty-dev/goatty-registry) (the official registry) and [goatty-plugin-template](https://github.com/goatty-dev/goatty-plugin-template) (start here to write one; includes a Claude Code skill).

## What a plugin can do

| Mechanism | Manifest | Generated by goatty | Permission |
|---|---|---|---|
| Install programs | `[[package]]` + `[[package.asset]]` (url, sha256, size) | `tools/<pkg>/<version>/`, links in `bin/` (on PATH in goatty shells only) | `binaries` (reason required) |
| Install zsh plugins | `[[package]]` with `source` (a `.zsh` script) and `system_paths` | `plugins/<pkg>` → the package; sourced at the plugin's slot (a distro copy first) | `binaries` (reason required) |
| Load order | `zsh.load` (`line-editor`, `prompt`, `normal`, `last`), `zsh.after` | the plugin's code goes into that slot's file, after the named plugins | – |
| Settings | `[[setting]]` (bool, choice, integer, string, path, list) | controls on the Plugins page, values in `host.json` | – |
| Aliases | `[[alias]]` (command, args templates, `when`) | `alias -- name='cmd args…'`, only when the command exists | `aliases` |
| Environment | `[[env]]` (value template, `when`) | `export NAME='value'` before compinit | `env` |
| Config files | `[[file]]` (`lines` or `text`, optional `env` pointing at it) | a file in the generation, e.g. bat's `BAT_CONFIG_PATH` | `config-files` |
| Completions | `zsh.fpath` (directories in the plugin) | `fpath` entries before compinit | – |
| Shell code | `zsh.init` (a `.zsh` file in the plugin) | sourced at top level with `$goatty_settings` | `shell-code` (reason required) |
| Needs a system program | `[requires] commands` | integration only when present (`plugin:x missing` otherwise) | – |

Everything goatty writes itself is quoted: a setting value can never become shell syntax (`tests: values_cannot_escape_quotes` runs real zsh). The only code a plugin brings is its `zsh.init` file, which is shown in full before installing and re-checked against its approved checksum every time a configuration is built.

Not yet: application plugins (goatty commands, UI) need a runtime goatty doesn't have (category `application` is rejected; WASM later, plan §7). Tracked: prompt modules (#96), other shells (#103), macOS and zip/tar.xz (#97), dependency resolution (#94), update notifications (#95), more first-party plugins (#99), index expiry (#100), installing an imported profile's plugins (#101), install progress (#102), publishing the repos (#93).

## The manifest (`plugin.toml`)

The template's [`plugin.toml`](https://github.com/goatty-dev/goatty-plugin-template/blob/main/plugin.toml) explains every field in comments. In short:

```toml
schema = 1                      # format version; a newer one is refused ("needs a newer goatty")
id = "eza"                      # [a-z][a-z0-9-]{1,39}
name = "eza"
version = "1.0.0"               # the plugin's semver (bump on any change)
summary = "A modern ls: …"      # one line
description = """…"""           # a few sentences for the details view
publisher = "goatty"
homepage = "https://eza.rocks"
license = "EUPL-1.2"            # the tool's
keywords = ["ls", "files"]
category = "environment"        # or "prompt"

[compat]
goatty = ">=0.0.1"              # semver requirement
os = ["linux"]
shells = ["zsh"]                # default

[requires]
commands = ["docker"]           # must exist on the host; goatty won't install them
plugins = []                    # must be installed first

[[package]]
id = "eza"                      # tools/<id>/
version = "0.23.5"              # the tool's version
bin = ["eza"]                   # relative to the asset root; linked as bin/<name>
prefer_system = true            # default: use a copy already on PATH instead of downloading

# A zsh plugin instead (or as well): a script goatty sources at the plugin's
# load slot, after zsh.init ran (so init can set the variables it reads).
# source = "zsh-autosuggestions.zsh"     # relative to the asset root; linked as plugins/<id>/
# system_paths = ["/usr/share/zsh/plugins/zsh-autosuggestions/zsh-autosuggestions.zsh"]
#                                       # distro copies, checked first; only under /usr/, /opt/homebrew/,
#                                       # /opt/local/, /run/current-system/sw/, /nix/var/nix/profiles/

[[package.asset]]
target = "x86_64-linux"         # x86_64/aarch64 × linux/macos, or "any"
url = "https://github.com/…/eza_x86_64-unknown-linux-musl.tar.gz"   # https only
sha256 = "e06eeb…"              # checked before anything is unpacked
size = 1412332
format = "tar.gz"               # or "binary" (the download is the executable)
root = ""                       # directory inside the archive

[[setting]]
id = "icons"                    # host.json: plugins.eza.settings.icons
label = "File icons"
help = "A small icon before each name … needs a Nerd Font"
type = "choice"
default = "auto"
arg = "--icons={value}"
group = "Look"                  # heading on the page
advanced = false                # behind "Show advanced settings"
choices = [
  { value = "auto", label = "Automatic", help = "…" },
  { value = "never", label = "Never", arg = "" },   # per-choice arg ("" = none)
]
# integer: min, max, step, unit · string/path/list: placeholder · list: separator · bool: arg, arg_off

[[alias]]
name = "ls"
command = "eza"                 # a package executable or a required command
args = ["{args}"]
when = "replace_ls"

[[env]]
name = "_ZO_EXCLUDE_DIRS"
value = "{exclude}"             # empty → not exported

[[file]]
name = "config"
env = "BAT_CONFIG_PATH"
format = "lines"                # or "text" with template = """…"""
lines = ["{args}"]

[zsh]
init = "zsh/init.zsh"
fpath = ["zsh/completions"]
when = "completion"
load = "normal"                 # line-editor | prompt | normal (default) | last
after = ["fzf"]                 # in the same slot, load after these plugins when they're there

[permissions]
binaries = "eza is a program: goatty downloads its official release …"
shell-code = "…"
network = "…"                   # declare when the tool itself uses the network
```

Validation (`goatty_plugin::manifest::parse`) reports every problem with its path (`setting.icons.default: …`). It refuses unknown keys (typos), non-https URLs, malformed checksums, aliases for commands the plugin doesn't provide, environment variables that would change how everything behaves (`PATH`, `LD_*`, `ZDOTDIR`, `GOATTY_*`, …), files outside the plugin directory, symlinks, and files over 1 MiB (4 MiB per plugin).

### Templates

Used in alias `args`, `[[env]] value`, `[[file]] lines`/`template`:

| | Meaning |
|---|---|
| `{id}` | the value: strings as they are, bools `true`/`false`, lists joined with `separator` (default space) |
| `{id.arg}` | the setting's command-line argument(s): bool `arg` when on (`arg_off` when off); choice: the choice's `arg` or the setting's; lists: one per entry; nothing for empty values |
| `{args}` | every setting's arguments, in manifest order |
| `{value}` | inside a setting's own `arg` |
| `{{`, `}}` | literal braces |

As a whole list item, `{id.arg}`/`{args}` expand to zero or more items. Inside a string they're joined with spaces, each quoted for a POSIX shell where needed (for variables holding a command, like `FZF_DEFAULT_COMMAND`). `~` and `~/…` in path settings and list entries become the home directory.

Conditions (`when`): `id` (bool on), `!id`, `id=value`, `id!=value`; checked against the settings at validation.

### Settings at runtime

Stored values live in `host.json` under `plugins.<id>.settings` (an open map, so `goattyd settings set plugins.eza.settings.icons always` works too). When a configuration is built, each value is checked against the plugin's schema: a bad one falls back to the default and is reported (`plugins.eza.settings.git: expected a bool, got "yes"; using the default`), the others are kept, like every other setting. `plugins.<id>.enabled = false` keeps a plugin installed but out of the shell.

While a plugin's `zsh.init` runs, `$goatty_settings[<id>]` holds each value (lists joined with spaces) and `$goatty_plugin_dir` its directory in the generation; both are unset afterwards.

### Load order

Where a plugin's aliases, init code and package scripts go in the managed `.zshrc` (its environment and `fpath` always go into `plugins-early.zsh`, before `compinit`):

| `zsh.load` | File | Position | For |
|---|---|---|---|
| `line-editor` | `plugins-line-editor.zsh` | after `compinit`, before the prompt | tools that add widgets and key bindings: fzf, Atuin, autosuggestions |
| `prompt` | `plugins-prompt.zsh` | the prompt; goatty sets a small one when no prompt plugin loaded | Starship |
| `normal` (default) | `plugins.zsh` | after the prompt, before the user's aliases, integration and additions | most plugins |
| `last` | `plugins-last.zsh` | after `~/.config/goatty/zshrc` | what must wrap every widget defined before it: syntax highlighting |

Within a slot, a plugin loads after the ones its `zsh.after` names (when they're installed and on), otherwise built-in plugins first, then by id (`goatty_shell::plugins::load_order`; a cycle is broken, never hangs). An `after` naming a plugin in an earlier slot is always satisfied. In the generated block, the init code runs first, then each package's `source` script (found as `$_goatty_src[<pkg>]`), then the status is recorded.

## Permissions

goatty doesn't take a plugin's word for what it does. Permissions are derived from the manifest's contents (`goatty_plugin::permissions::derived`): a `[[package]]` *is* the `binaries` permission. The author must explain the powerful ones (`binaries`, `shell-code`, `network`) in `[permissions]`; using one without a reason, or declaring one the manifest doesn't use, fails validation. The install plan lists each permission with its meaning, the author's reason and the concrete details (programs, alias names, variable names, files).

`binaries` and `shell-code` run code with the user's privileges. A registry signature proves where a plugin came from and that it wasn't changed; it doesn't make a program harmless. That's what the registry review ([REVIEW.md](https://github.com/goatty-dev/goatty-registry/blob/main/REVIEW.md)) and the approval step are for.

## Registries and trust

A registry is a Git repository:

```
registry.toml               name, trusted public keys (Ed25519, hex), yanked "id@version"s
plugins/<id>/<version>/     plugin directories; published versions are never edited
index.json                  every plugin version with the sha256 of each of its files, a sequence number
index.json.sig              {"key", "signature"} over the exact bytes of index.json
```

The chain of trust:

1. goatty pins the official registry's key (`goatty_shell::plugins::registry::OFFICIAL_KEYS`). Other registries are added with their key explicitly (`goattyd plugin registry add NAME URL --key HEX`); there's no trust on first use.
2. Refreshing downloads the registry (a `.tar.gz` of the repository, by default GitHub's archive of `main`; or an absolute directory) into a temp dir, then checks the signature by a trusted key, the format, the `sequence` (lower than the stored snapshot's → refused, so an old index can't be replayed), and the sha256 of every listed file. Only then are exactly the listed files copied into `~/.local/share/goatty/registries/<name>/`. On any failure the old snapshot stays.
3. The index pins every plugin file; the manifest pins every download.
4. A plan carries a digest over everything security-relevant (id, version, source, every file's checksum, every download URL + checksum, whether a system copy is used, permissions, the shell code). Installing sends the digest back; goatty recomputes the plan and refuses if it differs ("changed since you reviewed it"). What gets installed is exactly what was approved.
5. Installed files are kept with their checksums in `installed/lock.json`. Each configuration build checks the files it sources again; a changed file takes the plugin out with an issue instead of sourcing it.

Signing happens offline: the maintainer runs `scripts/publish.sh <secret key>` (validate, re-download every asset, `index build`, `index sign`, `index verify`) and commits the index. The registry's CI verifies the signature against the pinned key, validates every plugin and checks every download, but never holds the key. Contributors' pull requests only add plugin directories. Key rotation: add the new key to `registry.toml` and `OFFICIAL_KEYS`, release, sign with the new key, later drop the old one.

`registries.json` (`$XDG_CONFIG_HOME/goatty/`) holds added registries; `"builtin": false` turns the official one off (an organization that only allows its own registry, or tests).

## On a host

```
~/.local/share/goatty/
  registries/<name>/          verified registry snapshots (.fetched: when)
  installed/<id>/             verified copy of each installed plugin's files
  installed/lock.json         version, source, file checksums, packages, permissions, approved digest
  tools/<pkg>/<version>/      unpacked packages (built-in and installed plugins')
  bin/<exe>                   → tools/…; a link owned by another package or a user file is never replaced
  plugins/<pkg>               → tools/<pkg>/<version>/<root>, for packages with a `source` script
  current/zsh/
    plugins-early.zsh         fpath + exports (sourced before compinit), `off` for turned-off built-in plugins
    plugins-<slot>.zsh        aliases + init code + package scripts, per plugin guarded by
                              `(( $+commands[...] && ${+_goatty_src[...]} ))`; plugins.zsh is the normal slot
    plugins/<id>/…            generated config files and the plugin's shell files
```

Load order in the managed `.zshrc`: options, history, PATH, **plugins-early.zsh**, keys, compinit, (user .zshrc), **plugins-line-editor.zsh**, **plugins-prompt.zsh** (or the fallback prompt), **plugins.zsh**, the user's aliases, integration, the user's `~/.config/goatty/zshrc` (so the user can override a plugin's alias), **plugins-last.zsh**. `goatty-status` reports each installed plugin as `plugin:<id>` and each built-in one as `<id>` (ok with the command's or script's path, `missing`, or `off`); `goatty-setup` and the missing-tools hint only concern the built-in plugins marked for default install.

Install (`HostService::install_plugin`): lock `installed/.lock` → recompute the plan and compare the digest → download each package not already on PATH, verify, unpack to a staging dir, link → copy the plugin's files (verified) → update the lock → enable it in `host.json` and build a validated generation (`zsh -n` on every `.zsh`, including the plugin's) → offer to reload running shells. A failure undoes the packages this attempt added. Updating is the same with a newer version: packages the new version dropped are removed. Uninstall removes packages (unless another plugin needs the plugin), files, the lock entry and the `host.json` entry, then rebuilds.

Conflicts are refused at plan time: a plugin id, package id or executable of a built-in plugin (`starship`, `atuin`, `fzf`, …), another plugin's executable, or a file in `bin/` goatty didn't create. Alias names shared with another plugin or an existing command are warnings in the plan.

## Built-in plugins

autosuggestions, syntax-highlighting, starship, atuin and fzf come with goatty (`crates/goatty-shell/plugins/<id>/`, compiled in by `goatty_shell::builtins`; table with pins and slots in [`managed-zsh.md`](managed-zsh.md#installing-tools)). They're ordinary manifests (validated by the same parser, `builtins::tests`), so they get install plans, settings on the Plugins page and load-order slots. The differences:

- **Always there.** No lock entry and no copy in `installed/`: their files are part of goatty, read from the binary when a generation is built. They're on unless `plugins.<id>.enabled` is `false`; `goattyd plugin disable atuin` (or the switch on the Shell/Prompt/History page) turns one off, and `goatty-status` says `off`. Uninstalling is refused; `goattyd shell uninstall <id>` removes goatty's download of the tool.
- **Planning one = its packages.** `find("atuin")` always resolves to the built-in plugin (a registry can't shadow it). Its plan lists each package as already on the system, already installed by goatty at the pinned version (`current`), or to download; installing downloads only the latter. `goattyd shell install` and `goatty-setup` use exactly this.
- **Works with system copies anywhere.** Only a download needs a build for the host, so on macOS a Homebrew Starship is used even though goatty has no managed build there (#97).
- **Updates come with goatty releases**, like the pins did. After a pin bump, `goattyd plugin list` and the Plugins page show the older managed copy with an Update button (#45).
- Their packages keep the ids of the old tool table, so installs made before #98 are found where they are. Their init code may use goatty's own variables (`$_goatty_dir` for the generated `starship.toml`); registry plugins shouldn't.

## Using it

**GUI:** Settings → **Plugins** (`Ctrl+,`, or the palette: "Plugins: browse, install and configure"). Installed plugins show their settings as controls (toggles, segmented choices or a list for more than four, steppers, text fields), grouped, with help text; edits go into the same host draft as the Shell page (Preview/Apply). Available plugins show permission badges; **Review & install…** shows the plan (downloads with checksums, permissions with reasons, aliases, environment, "Read the code" for shell code, warnings) with **Install**/**Cancel**. Uninstall asks twice. With a remote goattyd all of this happens on that host.

**CLI** (`goattyd plugin …`, on the host):

```
search [QUERY] [--refresh]        what the registries offer
info ID                           details, settings with help, permissions
install ID[@VERSION]… [--yes]     print the plan, ask [y/N] (no terminal: needs --yes)
install --path DIR                a local plugin (marked "local, unverified")
update [ID…] [--yes]              newer versions, same review
uninstall ID…
list                              installed, enabled, updates, problems
enable|disable ID
set ID KEY VALUE | unset ID KEY   checked against the plugin's schema
registry list|refresh|add NAME URL --key HEX|remove NAME
```

**Authors** (`goatty-plugin`, `cargo install --git https://github.com/goatty-dev/goatty --locked goatty-plugin`): `new ID`, `validate [DIR]`, `render [DIR] --set k=v`, `hash URL|FILE…` (sha256, size, executables in the archive), `check-downloads [DIR…]`; maintainers: `index build|sign --key|verify [--trust HEX]|check`, `keygen FILE`.

## Protocol (v5)

`ClientMsg::Plugin { req, request }` → `ServerMsg::Plugin { req, reply }`, both JSON (`goatty_plugin::api::{Request, Reply}`: `catalog`, `plan`, `install` with the approved digest, `uninstall` → `Catalog`, `Plan`, `Changed`). goattyd answers on a separate thread (installs download; the connection's input must not wait), and the client waits up to 10 minutes. New operations or fields don't need a protocol bump. Plugin settings travel with the host settings (`SetHostSettings`).
